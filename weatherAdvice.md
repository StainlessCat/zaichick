# Предложение по реализации температуры окружающей среды в ZAYCHICK

## Целевой сценарий

Развивать температуру окружающей среды как подтверждаемый производственный замер, а не просто автозаполняемое поле.

### 1. Разделить два типа данных

- **Фактическая температура при сварке** — вводится ответственным на площадке с датой и временем измерения, местом/постом, прибором и источником.
- **Среднесуточная температура станции** — архивная справочная величина. Она полезна для сверки и восстановления данных, но не должна незаметно подменять температуру в момент работ.

Сейчас паспорт использует значение по дате из архива, а источник записан строкой `weatherSource` (`src/components/JointPassportModal.tsx`, `src/types/welding.ts`). Требуемый вид показателя нужно согласовать с проектом и применимой формой журнала.

### 2. Сохранять происхождение каждого значения

Вместе с температурой хранить источник, дату/время получения, идентификатор станции или прибора, тип данных (наблюдение, справка УГМС, ERA5), а для ручного ввода — автора и основание. При необходимости прикладывать документ или ссылку на акт/журнал измерений. Для этого лучше расширить модель данных, а не помещать все сведения в одну строку `weatherSource`.

### 3. Сделать понятный приоритет источников

1. Замер при сварке — основной производственный факт.
2. Официальный архив станции или справка УГМС — подтверждённые справочные данные.
3. ERA5 — только отдельный явно маркированный реанализ.
4. Нет данных — показывать отсутствие, не подставлять расчётное значение.

В текущей загрузке архива Meteostat требуется API-ключ, но UI-вызовы его не передают (`src/components/FacilityLocationModal.tsx`, `src/utils/weatherService.ts`). Ключ следует хранить только на сервере и предоставить приложению внутренний API для запроса архива.

## Улучшения интерфейса

- В паспорте показывать значение, единицы, источник и статус подтверждения; ручной ввод и архивное значение не смешивать.
- При отсутствии данных дать действие «Внести замер» и пояснить обязательные реквизиты.
- Не менять сохранённую температуру при открытии или редактировании старого паспорта. Сейчас эффект может заменить её значением архива либо очистить, если архивной записи нет (`src/components/JointPassportModal.tsx`). При изменении архива предлагать сравнить значения и подтвердить замену.
- Для массового обновления оставить отдельное подтверждение и добавить предпросмотр: сколько стыков изменится и какие старые значения будут заменены.
- В журнале и экспорте указывать только подтверждённые реквизиты источника. Не создавать видимость документального подтверждения автоматически.

## План внедрения

### Этап 1 — надёжность

Не перезаписывать сохранённые значения, добавить серверное хранение реквизитов происхождения и заметный статус «нет данных / ожидает подтверждения / подтверждено». Исправить интеграцию Meteostat через серверный API.

### Этап 2 — оперативный ввод

Добавить форму замера при сварке с временем, прибором/постом и автором; аудит изменений и возможность приложить документ.

### Этап 3 — документы и контроль

Выводить происхождение температуры в паспорт/журнал, добавить поиск стыков без подтверждённых данных, отчёт по температурным отклонениям и архив по объекту.

Начать рекомендуется с первого этапа и тестов на два риска: повторное открытие паспорта не меняет зафиксированное значение; недоступность метеосервиса не приводит к ложной температуре или статусу успешной загрузки.
