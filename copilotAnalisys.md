# Анализ системы ZAYCHICK: аудит кода и пользовательских сценариев

Дата анализа: 10.11.2026

## Вывод

Система покрывает основной производственный маршрут: лайнлист → техкарта и сварщик → паспорт стыка → ВИК/НК и ремонт → журнал. Однако пока рано считать её надёжным источником исполнительной документации: обнаружены риски повторной нумерации, ложного зачёта НК, неподтверждённых реквизитов в журнале и незаметной работы без синхронизации с сервером.

Анализ основан на исходном коде и сохранённых в репозитории артефактах симуляции. Скриншоты в `data/simulation_screenshots/` относятся к старому прогону (отчёт датирован 08.11.2026), поэтому не подтверждают внешний вид или поведение текущей версии интерфейса. Браузерная симуляция повторно не запускалась, поскольку сценарий работает с постоянной БД и не изолирует тестовые данные. Рабочие данные не менялись.

## Наиболее важные замечания

### 1. Повторяющиеся номера стыков и недостоверный UAT — высокий приоритет

На приложенных скриншотах реестра номера 901 и 902 многократно повторяются в одной линии:

- `data/simulation_screenshots/03_master_joints_added.png`
- `data/simulation_screenshots/05_ndt_inspection_repair.png`

В SQLite таблица ограничивает уникальность только `id`, а не сочетание «линия + номер стыка» (`src/server/sqliteDb.ts`, таблица `weld_joints`). E2E-сценарий выбирает первый найденный паспорт (`.first()`), не требует успешного HTTP-ответа на сохранение и записывает `success: true` без проверки результата для ряда этапов (`scripts/run_role_simulation_e2e.cjs`). Итоговый `SUCCESS` поэтому не подтверждает корректность сценария; отчёт также датирован 8 ноября (`data/simulation_screenshots/simulation_result.json`).

**Рекомендация:** запрещать дубли на сервере и при импорте, отдельно сообщать о уже существующих коллизиях; E2E запускать на временной БД с проверкой количества записей и фактически сохранённых полей.

### 2. Незавершённый НК может засчитываться в квоту — высокий приоритет

В расчёте линии результат «В работе» считается наличием РК/УЗК, потому что проверяется лишь непустое значение (`src/utils/readiness.ts`). Проверка на бизнес-функции подтвердила крайний случай: при требовании РК 100% один стык со статусом «В работе» дал `rkControlled: 1`, `rkRequired: 1`, `ndtStatus: sufficient`, дефицитов по сварщику нет.

**Рекомендация:** засчитывать контроль только по завершённым результатам; отдельно определить, как учитывать «Ремонт», повторный контроль, комбинированные методы и квоты по каждому сварщику.

### 3. Журнал может содержать автоматически придуманные номера заключений — высокий приоритет

Если фактический номер документа не заполнен, формирователь подставляет `ВИК-<номер стыка>`, `<метод>-<номер стыка>` и аналогичные реквизиты ремонта (`src/utils/journals.ts`). В печатной форме это выглядит как номер документа, хотя в системе может не существовать.

**Рекомендация:** не генерировать реквизиты, имитирующие номера протоколов; оставлять отсутствие незаполненным и показывать предупреждение/блокировать выпуск журнала, если обязательный реквизит отсутствует.

### 4. Критичные проверки не являются серверным барьером; часть ошибок — только предупреждения

Полная проверка вызывается в UI перед сохранением (`src/components/JointPassportModal.tsx`), но серверный метод сохранения стыка не вызывает её (`src/server/sqliteDb.ts`). Кроме того, просроченный НАКС и сварка до даты допуска формируют `warning` (`src/utils/dataIntegrityGuard.ts`), а сохранение блокируется только при наличии ошибок.

**Рекомендация:** перенести критические доменные проверки на сервер; определить формальный порядок для просроченных/невыданных допусков и требовать документированное разрешение отклонений, а не только показывать предупреждения.

### 5. При недоступности сервера изменения могут остаться только в браузере — высокий приоритет

При ошибке приложение применяет сохранение локально (`src/App.tsx`); синхронизация переводит статус подключения в ошибку, а часть отказов отображает лишь в консоли (`src/hooks/useServerSync.ts`). Для инженера это риск принять локальное изменение за запись в общей БД.

**Рекомендация:** постоянный заметный индикатор «не синхронизировано», число ожидающих изменений, повторная отправка и запрет считать экспорт/журнал официально сформированным до подтверждения сервера.

### 6. Метрика готовности может не совпадать с процентным планом НК

`isJointFullyAccepted` требует «Годен» по первичному НК для каждого стыка (`src/utils/readiness.ts`), а завершение линии требует, чтобы приняты были все стыки. Если для линии предусмотрен выборочный контроль, выполнение плановой квоты само по себе не закроет готовность линии.

**Рекомендация:** согласовать логику с принятой в проекте методикой и явно разделить статусы «квота НК выполнена» и «каждый стык принят».

## Проверка и пользовательский сценарий

- `npm test`: 38 тестов пройдены.
- `npm run lint`: пройдено.
- `npm run build`: успешно, но Vite предупреждает о крупных чанках: демонстрационные данные около 2,64 МБ, PDF-компонент около 1,62 МБ и основной чанк около 0,99 МБ. Для площадок с нестабильной связью стоит рассмотреть отложенную загрузку PDF и демоданных.
- Старые скриншоты показывают экраны ПТО, справочник сварщиков/техкарт, реестр, лайнлист и журнал, но не являются проверкой текущего интерфейса (в том числе актуального логотипа). Они также не доказывают корректное сохранение статусов НК и ремонта: скриншот этапа, названный проверкой НК, показывает реестр, а не паспорт с результатами. Записанный отчёт симуляции в этом отношении ненадёжен.

## Итоговая оценка

Хороший функциональный прототип с широкой предметной моделью, но перед применением для выпуска исполнительной документации в первую очередь необходимы:

1. защита уникальности стыков;
2. исправление зачёта НК;
3. достоверные реквизиты журналов;
4. явная индикация несинхронизированных данных.

Также нужна отдельная сверка форм и правил с актуальными контролируемыми экземплярами НТД и требованиями конкретного проекта.

# Повторный анализ после перехода на ZAYCHICK 2.0

Дата анализа: 12.11.2026

## Область и актуальность

В коммите `1ebd9de` архитектура изменена на FastAPI + PostgreSQL, добавлены REST API, JWT в HttpOnly cookie, SSE и отдельный Python-мигратор из SQLite. Прежние замечания выше относятся к версии до этого перехода и не должны автоматически трактоваться как описание текущей логики. В этом повторном анализе проверены новый backend, подключение фронтенда к API, миграция данных, пользовательский вход и доступные проверки.

## Блокирующие замечания

### 1. Изменения в большинстве API-запросов не фиксируются в PostgreSQL — критично

`get_db_session()` открывает SQLAlchemy-сессию и только выдаёт её обработчику; при выходе из контекстного менеджера сессия закрывается без `commit` ([database.py](./backend/app/core/database.py)). При этом обработчики создания/изменения/удаления стыков, лайнлиста, объектов, ЛРВ, НАКС и техкарт вызывают `flush`, но не `commit` (например, [joints.py](./backend/app/api/routes/joints.py), [facilities.py](./backend/app/api/routes/facilities.py), [lines.py](./backend/app/api/routes/lines.py)). В отличие от них, аутентификация и некоторые пользовательские операции явно фиксируют транзакцию.

После успешного HTTP-ответа несохранённая транзакция будет отменена при закрытии сессии. Пользователь может увидеть успешное сохранение, но после обновления страницы или нового запроса вернуть исходные данные. SSE-события публикуются до фиксации транзакции, поэтому подписчики также могут обновиться по ещё не сохранённой записи. Нынешние тесты с фальшивой in-memory-сессией не моделируют rollback при закрытии.

**Что исправить:** определить единую границу транзакции (например, commit/rollback на уровне зависимости или явный `session.begin()` в endpoint/service), публиковать события только после успешного commit и добавить интеграционный тест на реальной тестовой PostgreSQL: создать/изменить/удалить запись, закрыть исходную сессию и проверить результат из новой.

### 2. Штатные сценарии запуска не запускают FastAPI/PostgreSQL — критично

Фронтенд отправляет API-запросы на FastAPI; для dev-режима Vite проксирует `/api` на порт 8000 ([vite.config.ts](./vite.config.ts)). Но `npm start` по-прежнему запускает `tsx server.ts`, Windows-скрипт запускает тот же старый Express/SQLite сервер ([package.json](./package.json), [Запустить_ZAYCHICK.bat](./Запустить_ZAYCHICK.bat)), а Dockerfile и Compose собирают/поднимают Node-сервер с томом SQLite ([Dockerfile](./Dockerfile), [docker-compose.yml](./docker-compose.yml)). В них нет FastAPI-сервиса и PostgreSQL. README также описывает прежнюю архитектуру ([README.md](./README.md)).

**Влияние для пользователя:** открытие системы штатным bat-файлом или через описанный Docker Compose не гарантирует доступ к новому backend; вход и основные операции 2.0 будут обращаться не к тому сервису. Необходимо согласовать единый dev/demo/production запуск, прокси и healthcheck с новой архитектурой и обновить инструкции установки.

### 3. Нет понятного первичного развёртывания пустой PostgreSQL — критично

На старте FastAPI проверяет только доступность PostgreSQL; lifespan не запускает Alembic и не создаёт начальную учётную запись ([main.py](./backend/app/main.py)). Миграция схемы находится отдельно в Alembic, а заполнение существующими данными предлагается отдельной CLI-командой. Для новой пустой БД в проекте не обнаружен безопасный bootstrap-процесс администратора. Параметр `INITIAL_ADMIN_PASSWORD` из backend-примера окружения не используется в приложении.

**Влияние:** администратор не сможет войти, создать пользователей или подготовить справочники, пока оператор вручную не настроит схему и не создаст учётную запись вне UI. Нужен документированный и безопасный bootstrap, не создающий известный пароль по умолчанию.

### 4. Мигратор не сохраняет возможность входа существующих пользователей — высокий приоритет

Старая система хранит Scrypt-хеш в `passwordHash` и соль отдельно ([serverAuth.ts](./src/server/serverAuth.ts)). Мигратор читает `password` или `passwordHash`, распознаёт только Argon2-строку, а любое другое непустое значение, не начинающееся с `$`, хеширует как обычный пароль ([sqlite_migrator.py](./backend/app/services/sqlite_migrator.py)). В результате 64-символьный Scrypt-хеш будет принят за введённый пароль; поле соли старой системы при этом не используется. Пользовательский исходный пароль после миграции не подойдёт, а флаг обязательной смены пароля для этой ветки не включается.

**Что исправить:** реализовать проверенную конвертацию старого формата с использованием сохранённой соли либо явно переводить такие учётные записи в контролируемый процесс восстановления/сброса пароля. До запуска миграции вывести количество затронутых аккаунтов и обеспечить оператору способ безопасно выдать новые учётные данные. Добавить тест с реальным legacy-хешем, солью и проверкой входа после миграции.

## Остаточные риски и вопросы для производства

### SSE не обеспечивает заявленную межпроцессную доставку — средний приоритет

Событийная шина хранит подписчиков только в памяти текущего процесса. Хотя код содержит опциональный `pg_notify`, вызовы не включают его, а слушателя PostgreSQL `LISTEN` в backend не обнаружено ([event_bus.py](./backend/app/services/event_bus.py)). При запуске нескольких worker-процессов изменение в одном worker не будет гарантированно доставлено клиентам, подключённым к другому. Нужна реализация PostgreSQL pub/sub или внешней шины и тест минимум с двумя независимыми подписчиками/процессами.

### Интерфейс входа сохраняет следы демонстрационного режима — средний приоритет

В форме входа остались текст «Базовый пароль: 123», локальный список демонстрационных аккаунтов и предзаполнение пароля `123` ([LoginModal.tsx](./src/components/LoginModal.tsx)). Быстрый выбор аккаунта меняет локальный UI и затем запускает проверку серверной сессии; это не является серверной аутентификацией, но вводит пользователя в заблуждение. Кроме того, успешное создание пользователя закрывает форму, не выполняя вход, хотя кнопка обещает «Зарегистрировать и войти в сессию».

**Что исправить:** удалить быстрый вход по локальным seed-аккаунтам и упоминания общего пароля; после регистрации либо действительно выполнить вход, либо явно сообщить, что учётная запись создана и требуется отдельный вход. Проверить, что до авторизации демонстрационные производственные данные не воспринимаются как данные действующего объекта.

### Проверка масштаба загрузки

Список стыков сначала полностью загружается из БД, затем ограничивается страницей в Python ([joints.py](./backend/app/api/routes/joints.py)). На объектах с большим реестром это увеличивает память и задержки API. Следует перенести `LIMIT/OFFSET` и подсчёт в SQL и проверить интерфейс на объёмах, характерных для реального проекта.

## Результаты проверок

- `npm test` — 50 тестов пройдены.
- `npm run lint` — пройдено.
- `npm run build` — сборка успешна; остаются предупреждения Vite о крупных чанках.
- Python backend-тесты запустить не удалось: в окружении установлен только Python 3.10.5, тогда как backend требует Python 3.12+, и пакет `pytest` отсутствует. Поэтому результаты frontend-команд не подтверждают корректность нового backend.
- Рабочая копия содержала изменение `package-lock.json` до начала этой проверки; файл не изменялся в ходе анализа.

## Итог

Переход на реляционную PostgreSQL-модель, явную серверную RBAC и отдельный API — хорошее архитектурное направление. Но текущая версия **не готова к рабочему применению** до исправления фиксации транзакций, подключения новых сервисов в штатных сценариях запуска, подготовки пустой БД и восстановления входа существующих пользователей после миграции. Перед использованием для исполнительной документации дополнительно требуется прогнать backend-интеграционные тесты на PostgreSQL и сверить расчёты квот НК и формы журналов с применяемыми на объекте контролируемыми НТД.
