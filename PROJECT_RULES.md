# Свод правил разработки и архитектурный манифест системы «zaychick»
*(Учёт сварочных работ, неразрушающего контроля и исполнительной документации)*

Данный документ фиксирует незыблемые правила, стек технологий, отраслевые стандарты, ролевую модель (RBAC), бизнес-логику и дизайн-код проекта для гарантированного сохранения контекста при любых доработках.

---

## 1. Технологический стек и инфраструктура

| Уровень | Технологии | Назначение / Особенности |
|---|---|---|
| **Frontend** | React 18 / 19, TypeScript (Strict Mode), Vite, Tailwind CSS, Lucide React | SPA-архитектура, высокая скорость отклика, строгая типизация интерфейсов `WeldJoint`, `LRVItem`, `ProjectLineItem` и др. |
| **Backend & СУБД** | Node.js (v22–v26), SQLite 3 (Native WAL via `node:sqlite`), Express/Vite Dev Middleware | Локальная транзакционная СУБД `data/zaychick.sqlite` в режиме WAL (`journal_mode = WAL`, `synchronous = NORMAL`, `busy_timeout = 5000`). Fallback: транзакционный JSON WAL. |
| **Параллелизм & Синхронизация** | Оптимистическая блокировка (OCC), 3-way Auto-Merge, HTTP 409 | Версионирование каждой записи через `version`, `updatedAt`, `updatedBy`. Автоматическое бесконфликтное слияние независимых полей разных ролей при коллизии. |
| **Безопасность** | Соленое крипто-хеширование паролей (SHA-256 + salt), сессионные токены, Field-Level RBAC | Никаких паролей в открытом виде; разделение доступа на уровне конкретных полей каждого объекта. |

## 2. Отраслевые нормативные стандарты и формулы

### 2.1. СТО Газпром 15-1.1-002-2023 (Форма Г.1 — Журнал сварочных работ, 49 граф)
1. **Графа 4 и 5**: Диаметр и толщина стенки Элемента 1 и Элемента 2 указываются с новой строки.
2. **Графа 6**: ГОСТ/ТУ марки стали и завод-изготовитель берутся строго из базы ЛРВ (для каждого элемента с новой строки).
3. **Графа 8**: Наименование элемента. Если элемент — **фланцевая ЗРА**, пишется `«Фланец [наименование ЗРА]»` (например, *«Фланец крана шарового DN50 PN160»*).
4. **Графа 10**: Длина каждого свариваемого элемента в метрах (вводится вручную, с новой строки).
5. **Графа 13**: Номер стыка (основные: 010, 020, 030...; доборные: 011, 012...).
6. **Графа 14**: Дополнительная маркировка: для угловых швов по ГОСТ 16037-80 (У2..У20) пишется **`«Я»`**, во всех остальных случаях — **`«н/п»`**.
7. **Графа 16**: Номер технологической карты (ОТК) **без положения при сварке**.
8. **Графы 19 и 36**: **Только фамилия** мастера/прораба без должности и инициалов (функция `extractSurnameOnly`).
9. **Графы 20 и 37**: Пустые ячейки для физической подписи (без плейсхолдеров).
10. **Графы 21–23**: Первичный визуально-измерительный контроль (ВИК).
11. **Графы 24–27**: Первичный физический контроль (НК: РК, УЗК, РК+УЗК, ПВК, МК).
12. **Графы 28–31**: Независимый дублирующий контроль первичного шва (только для годных швов!).
13. **Графы 32–37**: Сведения об устранении дефекта и ремонтной сварке (заполняет мастер СМР / инженер ПТО).
14. **Графы 38–48**: Приемка стыка **после ремонта** (графы 38–40: ВИК ремонта; графы 41–44: основной НК ремонта; графы 45–48: дублирующий НК ремонта — заполняет дефектоскопист ЛНК).

### 2.2. Правило дефектного стыка и дублирующего контроля (Критическое отраслевое правило)
> [!IMPORTANT]
> **Если первичный контроль (ВИК или основной НК) выявил брак («Ремонт» или «Вырезать»):**
> * Дублирующий контроль исходного дефектного шва **НЕ ПРОВОДИТСЯ**. Шов сразу направляется на ремонт / вырезку.
> * Поля дублирующего контроля первичного шва принудительно сбрасываются: `dupNdtType = 'Не требуется'`, `dupNdtResult = 'Не проводился'`.
> * В журнале СТО Газпром графы 28–31 строго равны **`«н/п»`**.
> * В интерфейсе паспорта стыка селекторы дублирующего контроля скрываются/блокируются с поясняющей плашкой.
> * Повторный контроль (включая при необходимости дублирующий) проводится **только после ремонта** в специализированных графах 38–48.

### 2.3. Метод А расчёта эквивалентных дюймов (Equivalent Dia-Inch / EDI)
Формула расчёта трудоёмкости и сварочного объёма:
$$\text{EDI} = D_{\text{inch}} \times K_{\text{толщ}}(S)$$
где $D_{\text{inch}}$ — номинальный диаметр в дюймах, а $K_{\text{толщ}}(S)$ — отраслевой ступенчатый EPC-коэффициент по фактической толщине стенки $S$:
* $S \le 10\text{ мм} \implies K_{\text{толщ}} = 1.0$
* $10 < S \le 15\text{ мм} \implies K_{\text{толщ}} = 1.35$
* $15 < S \le 20\text{ мм} \implies K_{\text{толщ}} = 1.75$
* $20 < S \le 26\text{ мм} \implies K_{\text{толщ}} = 2.3$
* $26 < S \le 35\text{ мм} \implies K_{\text{толщ}} = 2.8$
* $35 < S \le 50\text{ мм} \implies K_{\text{толщ}} = 3.5$
* $S > 50\text{ мм} \implies K_{\text{толщ}} = 4.5$

### 2.4. Эталонное соответствие условных проходов DN и наружных диаметров Dн
Соответствие диаметров трубы/детали $D_{\text{н}}$ условному проходу $DN$:
* $16 \to 10$ · $20 \to 15$ · $26 \to 20$ · $32 \to 25$ · $42 \to 32$ · $45 \to 40$ · $57 \to 50$ · $76 \to 65$ · $89 \to 80$ · $108 \to 100$ · $114 \to 100$ · $133 \to 125$ · $159 \to 150$ · $219 \to 200$ · $273 \to 250$ · $325 \to 300$ · $377 \to 350$ · $426 \to 400$ · $530 \to 500$ · $630 \to 600$ · $720 \to 700$ · $820 \to 800$ · $920 \to 900$ · $1020 \to 1000$ · $1220 \to 1200$ · $1420 \to 1400$ · $1620 \to 1600$.

### 2.5. Правила работы с метеоданными и архивом температур
1. **Категорический запрет на климатические формулы в архиве:** Запрещается использовать расчётные/климатические математические формулы для подстановки температуры в паспорт стыка или журнал. В архив заносятся **только фактические наблюдения конкретной метеостанции**. Если наблюдений нет — фиксируется статус **«нет данных»** (поле остаётся незаполненным).
2. **Офлайн-реестр станций Росгидромета РФ (100% автономность):** Встроенная база ключевых опорных станций Росгидромета/WMO по всем 8 федеральным округам (от Кургана и Вологды до Бованенково и Сабетты) обеспечивает работу в закрытом интранет-контуре без выхода в интернет.
3. **Поверенные метеопосты площадки (АМК):** Регистрация ведомственных автоматических метеокомплексов с указанием модели, номера свидетельства о поверке ФГИС «АРШИН» Госстандарта и срока действия.
4. **Официальные справки УГМС Росгидромета (Импорт CSV/Excel):** Парсер ведомостей фактических замеров актированной погоды с автоматическим определением дат (`ГГГГ-ММ-ДД` / `ДД.ММ.ГГГГ`), разделителей (`;`, `\t`, `,`) и десятичной запятой (`+18,2` $\to$ `+18.2 °C`).
5. **Основной онлайн-источник — Meteostat Daily API:**
   - Поиск реальных метеостанций по координатам объекта с выводом названия, расстояния (в км) и ID станции.
   - Запрос фактической среднесуточной температуры `tavg`. Обязательно отключать модельную интерполяцию/подстановку пропущенных значений (`model=false`).
   - Учёт задержки поступления архива (1–7 дней): для свежих дат возвращать статус «Данные ещё не поступили».
6. **Резервные источники (Open-Meteo ERA5):**
   - Данные реанализа по координатам допускаются только как отдельная явная опция с обязательной маркировкой: **«реанализ, не наблюдения метеостанции»**.
7. **Привязка к объекту и неизменяемость стыков:**
   - Станция подтверждается пользователем для конкретного объекта строительства.
   - Смена станции **не должна молча менять** уже сохранённые температуры сваренных стыков. Массовое обновление допустимо только по отдельной явной команде с подтверждением пользователя.
8. **Раздельная сигнализация сервиса:**
   - **Доступность сервиса:** *«На связи» / «Нет связи»*, время последней проверки и текст ошибки. Кнопка *«Проверить связь»*.
   - **Наличие данных:** *«Данные станции доступны за эту дату» / «За дату данных нет» / «Данные ещё не поступили»*.
   - При ошибке сети категорически запрещено незаметно подменять архив климатической оценкой.

## 3. Матрица разграничения доступа (Field-Level RBAC)

Система строго блокирует несанкционированную модификацию чужих полей на клиенте и сервере (`enforceFieldLevelRbacOnJointSave`):

| Роль в системе | Разрешённые поля стыка | Запрещённые поля (Read-Only) |
|---|---|---|
| **Инженер ПТО (`pto`)** | Геометрия стыка, привязка к линии/РД, элементы 1 и 2 из базы ЛРВ, длины, заводские номера, температура подогрева, дата ремонта, ТК ремонта. | Контроль качества (ВИК, НК, дублирующий контроль, контроль после ремонта), техкарты сварки. |
| **Технолог по сварке (`technologist`)** | Разработка и редактирование ТК сварки, допуск сварочных материалов, проверка аттестации сварщиков НАКС. | Изменение геометрии стыка, привязка элементов ЛРВ, внесение результатов НК. |
| **Дефектоскопист / Специалист ЛНК (`ndt`)** | Результаты, номера заключений, даты и дефектоскописты первичного ВИК/НК, дублирующего контроля, ВИК/НК после ремонта. | Геометрия стыка, привязка ЛРВ, параметры сварки, ТК сварки. |
| **Руководитель / Куратор (`manager`)** | Согласование, закрытие линий, генерация сводных отчетов готовности (штучный % и % EDI), экспорт журналов. | Прямая правка первичных протоколов без фиксации в аудите. |
| **Администратор (`admin`)** | Полный доступ ко всем модулям, сброс/восстановление БД, управление аккаунтами. | — |

## 4. Архитектура паспорта стыка (UI/UX и дизайн-код)

### 4.1. Фирменный стиль
* **Основной брендовый цвет чердака**: `#1e3799` (глубокий классический инженерный синий). Шапки окон, первичные кнопки действий.
* **Шрифт названий разделов в шапке**: открытый геометрический аналог Century Gothic с полной поддержкой кириллицы **Jost** с фолбэком на Century Gothic (`font-family: 'Jost', 'Century Gothic', CenturyGothic, AppleGothic, sans-serif`).
* **Основной шрифт интерфейса (`font-sans`)**: **Manrope** (`font-family: 'Manrope', -apple-system, BlinkMacSystemFont, sans-serif`) с нативной поддержкой кириллицы.
* **Фирменный логотип**: геометрический знак «Заяц — сварной стык трубопровода» и лаконичное имя **`zaychick`** строчными буквами без вспомогательных подзаголовков.
* **Статусные индикаторы**:
  * «Годен» — `text-emerald-700 bg-emerald-50 border-emerald-300`
  * «Ремонт» / «Вырезать» — `text-rose-700 bg-rose-50 border-rose-300`
  * «В работе» — `text-amber-700 bg-amber-50 border-amber-300`
  * «Не проводился» / «Не требуется» — `text-slate-500 bg-slate-100 border-slate-200`
* **Моноширинный шрифт (`font-mono`)**: обязателен для кодов ЛРВ, номеров стыков, шифров РД, дат, диаметров, толщин стенок и клейм.

### 4.2. Порядок смысловых блоков паспорта стыка
1. **Шапка**: Номер стыка, шифр РД, технологическая линия, статус готовности, быстрый переход к соседним стыкам линии ($\leftarrow$ / $\rightarrow$).
2. **Блок 1 «Сварочные работы»**: Способ сварки, дата, клеймо сварщика, материалы, температура воздуха (авто-метеопост/архив), подогрев, ответственное лицо, а также **Строка 4: Тип стыка (монтажный/цеховой) + Тип соединения по ГОСТ 16037-80 + Положение при сварке по НАКС**.
3. **Блок 2 «Свариваемые элементы»**: Элемент 1 и Элемент 2 строго из базы ЛРВ соответствующего шифра РД (автоподбор толщины стенки, диаметра, марки стали, ГОСТ/ТУ, завода-изготовителя, категории ЗРА и типа соединения).
4. **Блок 3 «Контроль качества»**: 3 подблока: Первичный ВИК, Первичный НК (РК/УЗК) и Дублирующий контроль (с автоблокировкой при первичном браке).
5. **Специализированный блок «Устранение дефекта и контроль после ремонта»**: Отображается только для дефектных стыков; разделен на:
   * Сведения о ремонте (статус, дата, ТК ремонта, клеймо ремонтника, мастер СМР) — **без обозначения граф («гр. 40» и т.п.)**.
   * Приемка после ремонта: ВИК ремонта и основной/дублирующий НК ремонта.
6. **Дополнительный блок ГОСТ 32569-2013** (аккордеон): контроль корня, стилоскопирование, термообработка, твердость, ферритная фаза.

## 5. Обязательный протокол верификации изменений

Перед передачей любых изменений пользователю или коммитом в репозиторий выполняется полный цикл валидации:

```bash
# 1. Проверка типов TypeScript (Strict)
npx tsc --noEmit

# 2. Модульные и интеграционные тесты отраслевой логики (36 тестов)
npm test

# 3. Production-сборка клиентского бандла
npm run build
```

Все проверки обязаны завершаться со статусом **PASS (0 ошибок, 0 предупреждений)**.

## 6. Принцип абсолютной фактологической достоверности и критического взгляда

> [!CAUTION]
> **При отчёте о выполненной работе запрещается придумывать результат и приукрашать ситуацию с программой. Только факты и критический взгляд.**

1. **Категорический запрет фальсификаций и приукрашиваний:** Запрещается выдумывать результаты тестов, сочинять ответы, приукрашивать реальное состояние кодовой базы или рапортовать о выполнении этапов, если они не подтверждены кодом и тестами на 100%.
2. **Только проверяемые факты:** Любой отчёт должен опираться исключительно на фактический вывод команд терминала (`npm test`, `npx tsc --noEmit`, `npm run build`), конкретные строки кода и проверенные физические файлы.
3. **Критический и объективный взгляд:** При обнаружении любых дефектов, ограничений архитектуры, регрессий или неполноты реализации ассистент обязан прямо, немедленно и открыто сообщать о них пользователю без попыток сгладить углы или замаскировать проблему.
4. **Запрет синтетических подмен:** Ни в коде, ни в отчётах не допускается заменять реальные физические данные (погодные станции, клейма сварщиков, результаты НК) скрытыми вымышленными значениями или непроверенными эвристиками без явного согласования.
